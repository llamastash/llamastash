### Good to have

- [x] ~~Daemon does not restart on ctrl+r~~ — `handle_restart_daemon` was waiting for the old daemon's socket to become unconnectable, but the daemon releases its lockfile _after_ the listener drops (accept-loop exit → drain → `stop_all_managed` → remove socket → drop lockfile). The replacement child's `acquire` raced into that window, hit a contended `flock`, exited with `AlreadyRunning`, and `start_detached` reported a failure with no new daemon coming up — the TUI then stuck on "daemon connecting…" until the user retried. ## General Roadmap

### High priority

- [ ] **`llamastash bench <model> [--preset a,b]`.** A quick speed number per preset, so a user can compare knob changes without the maintainer scripts in `scripts/bench/`. Per preset: start, wait for ready, send a fixed prompt N times, read the server-reported prompt and generation tok/s (same field lookup as live speed stats) plus a wall-clock first token, then stop what it started. Table on a TTY and `--json`. Open: cycling presets goes through admission and make-room, and a server that reports no speed fields gets clock-only numbers.
- [ ] **`llamastash ask <model> [-p "prompt"]` — one-shot prompt from the shell.** Start the model if it is dormant, stream the answer to stdout, then either leave it to the idle sweep or stop it with the launch. Accept stdin and `--file`, take `--system`, emit `--json` with the timings and token counts. Today a scripted prompt has to get the key (via `llamastash api-key` or `runtime.json`) and build its own OpenAI request: chat lives only in the TUI (`src/tui/tabs`, `src/tui/oai_client.rs`) and `start` has no prompt flag, so there is no `ollama run <model> "prompt"` equivalent. Open: go through the proxy (`/v1/chat/completions`, which gets routing, auto-start, fallback and residency for free) or straight to the launch port and re-implement the wait-for-ready.
- [ ] **`llamastash storage` — disk accounting and reclaim over every cache root.** `show` gives one model's size (shards summed); nothing answers "what is using my disk and what can I delete". Report per-root and per-model bytes across the roots `util::model_caches` already resolves (HF hub, Ollama, LM Studio) plus the llamastash cache dir (`logs`) and state dir (llama.cpp installs under `llama-cpp/bNNNN/`, `state.json`), split into catalog rows versus files nothing references, with `--dry-run` and `--free <SIZE>` that keeps favorites and stops at the target. Reuse `delete::plan_for_path` / `execute` for removal, which is TUI-only today (see the delete entry below). Open: each HF repo keeps its own `models--<owner>--<repo>/blobs/<etag>` with snapshot symlinks over it (`src/util/model_caches.rs`, `src/init/download.rs:20`), so the same weights pulled into two repos are two separate files; confirm with inode link counts before writing any reclaim logic, since the number a delete actually frees depends on that.
- [ ] **`llamastash update` and a version notice.** Flag a newer release, and install it where the channel allows. This is the binary, not the model-file check below, and it is separate from the backend install work (`init --install` channels are about llama.cpp). Nothing checks or updates llamastash itself. The binary ships four ways (install.sh mirror, Homebrew formula, Scoop bucket, crates.io: the `publish-site` / `publish-homebrew` / `publish-cargo` jobs in `release.yml`), so `update` has to detect its channel and defer to the manager (`brew upgrade llamastash`, `scoop update llamastash`) rather than overwrite a managed file; a `cargo install` build gets a printed instruction instead. The check is one GitHub API call, opt-in and off by default, skipped under `LLAMASTASH_OFFLINE`, and it must not slow `status` down: cache the answer and compare at most daily.
- [ ] **Model update notice.** Flag a cached HuggingFace model whose upstream file changed: `list --check-updates`, `pull --update`, and a TUI key. On demand only, with the result cached for 24 h. No timer by default, because the daemon makes no HuggingFace calls today (none in `src/daemon`, `src/discovery`, `src/proxy`). One small API request per cached repo. Compare the file's hash, not the repo commit, since a README edit also creates a new commit. A config interval for background checks can come later, off by default.
- [ ] **Sandbox spawned servers on Linux.** The supervisor only calls `setsid` and strips credential env vars before `exec` ([`src/daemon/supervisor.rs`](src/daemon/supervisor.rs)), so a child runs with the user's full file access. Add `PR_SET_NO_NEW_PRIVS` and a Landlock ruleset in `pre_exec`: read-only on the model dirs and the binary's install dir, read-write on the launch's log and state dir only. Most useful for the generic backend (it runs whatever `config.yaml` declares) and for GGUFs from untrusted repos. Needs a plan: GPU device nodes and driver caches (`/dev/dri`, `/dev/kfd`, `/dev/nvidia*`, shader caches), wrapper scripts that call `docker`, a per-backend allowlist behind a trait method, an opt-out knob, a fallback to no sandbox on a kernel without Landlock, and what macOS and Windows get (nothing at first).

- [ ] **`--llama-server` is never adopted on a Lemonade-enabled host.** `reconcile_binary_with_running_daemon` ([`src/cli/client.rs`](src/cli/client.rs)) reads a non-empty `status.models` as "managed launches are active", and the supervised Lemonade umbrella is one of those rows (`launch_id: lemonade-umbrella`), so wherever `lemond` resolves the flag is dropped with "Stop them and re-run to apply" — there is no launch for the user to stop. - [ ] **Admission prices the `--fit-ctx` floor while a launch loads, not the context `--fit` picks.** Qwen3.8-27B Q6_K (20.5 GiB) was projected at 25.0 GiB, then `--fit` chose 262144 ctx and GTT use reached 86.4 GiB (found 2026-09-27 testing #83). See [`project_demand`](src/launch/admission.rs) ("a floor, not a ceiling") and `spawn_admission_settle` in [`launch_service.rs`](src/daemon/launch_service.rs).
  - Merged 2026-09-30 from Auto-fit follow-ups (same problem, found earlier on the 80B):
    - [ ] **Floor-vs-fit over-allocation gap** — admission is a _pre-spawn_ check on the demand **floor** (`weights + KV-at-fit_ctx_floor + overhead`); `--fit-ctx` is a floor, not a cap, so post-spawn `--fit` can size the context _up_ (toward the trained window) and over-commit the GPU above what admission validated. A model whose floor fits can still OOM at load — proven live on the 80B (`qwen3next` Q5*K_M): admitted at its floor against ~85 GiB free, then `unable to allocate ROCm0 buffer`. Admission can't catch this (the sizing happens inside llama-server after spawn). Closing it needs the `--fit-target` margin + upstream absolute-budget flag under Auto-fit follow-ups (so fit respects llamastash's real pool), or an in-process load backstop. Distinct from the split-GGUF floor miscount fixed in Auto-fit follow-ups — a \_correct* floor still does not bound fit's upward sizing.
