# R18 Batch 3: media launch reporting + first-scan readiness

Date: 2026-11-01. Source: `TODO.md` § R18, Batch 3. Evidence:
[`docs/testing/2026-10-24-media-z13-sdcpp-flm.md`](../testing/2026-10-24-media-z13-sdcpp-flm.md) § Gaps.

## Goal

Three batch-3 items, all in how a launch is reported or when the catalog is usable:

1. A launch of an `stt`/`image` entry prints `MODE chat` in `llamastash status` while
   `list --json` reports the row's `mode_hint` correctly.
2. `llamastash start <entry>` right after `daemon start` fails with
   `no model matches ... (0 known)` until the first scan lands seconds later.
3. Bare OpenAI media names (`whisper-1`, `dall-e-3`) stop resolving once a second entry
   declares the same mode; the refusal is correct but says nothing about `proxy.aliases`.

## Scope and decisions

- **U1 — MODE column names what the entry answers.** `LaunchMode::resolve` maps a media
  hint to `Chat` on purpose (the mode is routing-only, no argv changes), so the launch's
  own mode is not the bug and stays as it is. The status launch row gains the catalog row's
  declared mode as an additive `mode_hint` field, and the human MODE cell prints that
  hint when it names a declared-only media mode (`image`/`tts`/`stt`), otherwise the
  launch mode as today. So an `stt` launch prints `stt`, a `--mode rerank` override on a
  chat row still prints `rerank`. Same source, same label as `list`'s
  `metadata.mode_hint`, so the two surfaces cannot disagree.
  Rejected: replacing `mode` in the row, which would make `--json` lose what the launch was
  actually started with.
- **U2 — `start` waits for the first scan.** The catalog gets a first-scan-completed
  signal; the discovery task sets it right after its initial `full_rescan`. A new read-only
  IPC method `catalog_ready {wait_ms?}` answers `{"first_scan": bool}` and blocks up to
  `wait_ms` for the signal. `start` asks once with `wait_ms: 0` (free fast path, no message
  in the normal case); if the scan is still running it prints one dim line and waits up to
  30 s, then resolves as before. Chosen over "make `daemon start` return after the scan",
  which would stall every client (including daemons spawned on demand by `list`) for the
  whole walk of a large library.
  Shortcut: the 30 s bound is a constant, not a config key; upgrade if a real library
  needs longer.
- **U3 — one sentence in the media docs.** The refusal is right; the gap is that the docs
  never say two entries cost the bare OpenAI names. Docs only, in the media paragraph of
  `docs/usage.md`. The refusal text itself is unchanged.

(`LLAMASTASH_STATE_DIR`/`CONFIG_DIR`/`CACHE_DIR`/`HF_HOME` under `target/e2e-b3`,
`--proxy-port 11499 --force`), running two generic entries whose binary is the
`fake_llama_server` fixture: `asr` with `modes: [stt]` and `plain` with none.

  `mode_hint` key.
- `catalog_ready` over the real socket: `{"first_scan":true}` with `wait_ms: 0`, with no
  params, and `-32602` for a params body that is not an object.
- First-scan wait, with a scan root of 3000 minimal GGUFs (the initial walk measured
  ~22 s here): `daemon start` then `start asr` typed straight away printed
  `waiting for the daemon's first model scan ...`, launched after 21.2 s, and the row read
  `stt`. Before the change the same sequence printed `no model matches asr (0 known)`.
- Five more fresh daemons with the normal (fast) scan: every immediate `start asr`
  succeeded, and no waiting line appeared.

All leftover daemons and fixture servers from this run were stopped; the machine's own
daemon was never touched.
