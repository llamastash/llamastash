# Review handoff: PR #72 — one knob registry, so CLI, TUI and presets cannot drift

**PR:** [#72](https://github.com/llamastash/llamastash/pull/72) (open)
**Branch:** `feat/knob-parity` @ `f0f30ef`
**Date:** 2026-08-28
**Engine verified against:** `llama-server` 0.3.0-dev, build 10656, commit 732707dff

Independent review: static read of the new modules plus a full four-surface E2E
against the real engine. Every argv assertion in this report was read from
`/proc/<pid>/cmdline`, never from llamastash's own output. File comparisons used
`cmp` — see the tooling hazard at the bottom for why `diff` is unusable on this
host.

## Verdict

The architecture is sound and the headline claim is real: a CLI launch, a preset
launch, and a TUI-cycled row produce byte-identical engine argv (cmp-verified on
distinct pids). But **finding 1 is a must-fix before merge**: the PR's own bug
list advertises it as fixed, it silently mis-launches, and it is exactly the
drift class this PR exists to eliminate.

## Findings

### 1. A preset's pinned `mode` still never applies at launch — all three surfaces

The PR description lists "`mode:` in a preset was dead config. Saved, parsed,
never applied" under *Bugs this found*. The storage half is fixed —
`presets show` returns `mode: "embedding"`, and `materialize_preset`
(`src/launch/presets.rs:132`) projects it onto `params.mode` with a unit test
pinning that. The launch half is not. Every path from a preset to a launch drops
it:

- **CLI**: `partial_params_from_preset` (`src/cli/start.rs:446`) reads
  ctx / reasoning / mtp / knobs / extras / backend / server from the preset
  payload — never `mode`. `resolve_mode` (`src/cli/start.rs:42`) decides from
  `--mode` or the catalog hint alone, so the payload ships the hint's mode.
- **Daemon**: `LaunchParams::new(parsed.model_path.clone(), mode)`
  (`src/daemon/launch_service.rs:374`) takes mode only from the wire. The
  no-selection inheritance block that covers extras / mtp / identity
  (`launch_service.rs:504-578`) does not cover mode, so a `default:` preset
  pinning a mode is equally dead.
- **TUI**: `seed_from_preset` (`src/tui/launch_picker.rs:401`) clones
  `p.knobs`, which materialization has already stripped mode (and ctx / mtp)
  out of.

Repro (verified live on `f0f30ef`):

```bash
# preset emb pins mode: embedding + n-gpu-layers: 99
llamastash start Phi-3.5-mini --preset emb --wait
llamastash status --json | jq '.models[].mode'        # "chat" — wrong
tr '\0' '\n' </proc/$PID/cmdline | grep embeddings    # absent; n-gpu-layers present
llamastash start Phi-3.5-mini --mode embedding        # works: --embeddings emitted
```

The result is arguably worse than before the PR: the config now faithfully
records a mode that silently never applies. The PR's 13-case E2E
(`docs/testing/2026-08-28-knob-parity-e2e.md`) has no preset-mode case, which is
how it slipped. Fix shape: read `mode` in `partial_params_from_preset` with the
same explicit-flag-wins ordering the identity fields got in `f0f30ef`, and give
the daemon-side default-preset inheritance a mode rung. Add the missing E2E
case.

### 2. The migration eats comments *inside* a preset entry body

`rewrite_entry` (`src/config/knob_migration.rs:172`) re-renders the whole entry
from the folded value, so a comment sitting **between two knobs of the entry**
is lost, while every comment above a key survives. Verified on a hand-annotated
config: 4 of 5 comments kept; the lost one was `# keep memory pinned` between
`flash_attn` and `mlock` inside a legacy entry.

The repo's coverage — `comments_between_entries_survive` in `knob_migration.rs`
and the yaml_edit span tests — only places comments above keys, which is exactly
the shape that works. "Comments survive" is true for the tested shape only.

Decision needed: either preserve in-body comments (hard — the body is
regenerated), or document the boundary ("comments above keys survive; comments
between an entry's own keys do not") and add a test pinning that behavior so it
is a choice, not an accident. `upsert_block`'s doc comment already admits the
analogous key-line-comment loss, so a doc line is consistent with the existing
contract.

### 3. `parse_value` accepts `NaN` for float knobs

`src/launch/knobs/value.rs:511-528`: `NaN < lo` and `NaN > hi` are both false,
so `--rope-freq-scale NaN` passes the range check and ships to the engine
verbatim. One-line fix: reject non-finite (`v.is_finite()`) with
`NotAFloat`. `inf` is already caught by the `max` check where a bound exists,
but unbounded float knobs take `inf` too — the same `is_finite` guard covers
both.

### Minor / theoretical (noted, not blocking)

- **No same-backend flag-collision check.** `registry::validate()`
  (`src/launch/knobs/registry.rs:302`) catches kind conflicts *across* backends
  but nothing rejects two knobs of one backend claiming the same flag spelling;
  the emitter would emit it twice. Current declarations are clean — this is a
  missing guard, not a live bug.
- **Direct-hit `Auto` is not re-validated.** The layer loop
  (`src/launch/knobs/resolve.rs:104`) stores `Auto` from a direct id hit without
  checking the destination declares an auto state; only the carry-over path
  (`carry_over`, resolve.rs:154) checks `def.has_auto()`. No current
  declaration triggers it (the shared `mtp` id has auto everywhere).
- **A kind-mismatched carry-over vanishes silently.** If a concept's value
  fails `parse_value` against the destination knob, it is neither set nor
  listed in `dropped` (the `carried` test in resolve.rs:124 marks the id as
  carried regardless of parse success). Needs divergent kinds on one concept —
  none today.
- **Legacy config reads before the first daemon start yield empty presets.**
  `fold_legacy_entry` is migration-only now; the loader parses
  `PresetBody { knobs, extras, backend, server }` and silently ignores
  everything else (no `deny_unknown_fields`). Between upgrading and the first
  `daemon start`, a CLI-only `presets show` on an unmigrated config reports
  empty knobs. Transitional, self-heals on first daemon start, worth a line in
  the migration announcement at most.
- **CRLF configs**: `trim_trailing_trivia` handles `\r` via `trim()`, but the
  rendered replacement lines are `\n`-only — a CRLF file goes mixed-line-ending
  after one edit. Cosmetic.

## Coverage caveats — what this review could NOT exercise live

This host has neither vLLM nor a ds4 binary installed, and no local GGUF
carries an MTP head that could launch cheaply. Verified by unit test + static
reading only:

- vLLM's volatile memory knobs (`kv-cache-memory-bytes`,
  `gpu-memory-utilization`) and the last-params replay guard
- backend/server inheritance on plain relaunch (stage 6 / `f0f30ef`) — only one
  server exists here, so inherited-vs-auto is indistinguishable live
- MTP-carrying launches (speculation group open, `mtp` resolving on, DSpark
  knobs)
- Lemonade's single-knob surface

## Tooling hazard noted during this review

`diff` on this host reports "[ok] Files are identical" (exit 0) for files with
different checksums — confirmed with `md5sum` + `git diff --no-index` +
`cmp` disagreeing with it. It is not the GNU diff its `type` claims. Anything
on this machine that gates on `diff` output (scripts, hooks, agent tooling) is
trust-compromised; use `cmp` or `git diff --no-index` until root-caused.
