## How to verify a finding before you fix it

Each entry gives a file:line and the call path. Read the path, don't trust the summary.
Project constraints that shape acceptable fixes:

- `CLAUDE.md` § backend no-leak contract: no backend id-string or name, in code **or
  comments**, outside `src/backend/<id>/`, `src/backend/mod.rs`, and the typed config
  struct. Several fixes below are tempting to write as `== "vllm"` — don't; use a trait
  method.
- `CLAUDE.md` § docs ship with code: a behavior fix updates the affected doc in the
  **same commit**, and ticks the `- [ ]` in the feature plan.
- Tests: `make test` (it carries `--features test-fixtures`; forgetting it is the
  classic failure). E2E for anything user-visible — a green suite is explicitly not
  sufficient here, and round 1 found defects the suite passed straight through.
- No backwards-compat paths until first release. Change the shape, don't add a fallback.

## Round 1 — full-branch review (14 findings, all open at `ebabd23`)

### Blocking

#### R1-1 · `gpu_memory_utilization` disables both memory guards

`src/backend/vllm/mod.rs:413`

```rust
if user_set(params, "kv_cache_memory_bytes") || user_set(params, "gpu_memory_utilization") {
  return out;
}
```

`resolve_native_knobs` returns early, so `kv_cache_memory_bytes` is never inserted. The
non-GGUF admission gate in `src/daemon/launch_service.rs:919-951` derives demand solely
from `admission::resolved_cache_bytes(&launch_params)`, which matches a knob id ending
in `cache_memory_bytes`. Absent here → `None` → `demand` is `None` → `try_admit` never
runs.

Net: `start <safetensors repo>` with `gpu_memory_utilization=0.9` on a 121 GB unified
host gets neither the byte cap nor a pre-spawn refusal. The commit pair "make the KV cap
fail safe" + "apply the admission gate to non-GGUF launches" both no-op on exactly the
configuration that has frozen this hardware before.

**Fix direction:** the two knobs are not interchangeable. `kv_cache_memory_bytes` set by
the user is a real opt-out; `gpu_memory_utilization` set by the user still needs the
admission gate to see a demand figure. Either derive a byte figure from the utilization
fraction and feed it to `resolved_cache_bytes`, or keep the gate engaged with the
pool-fraction demand computed separately.

#### R1-2 · Safetensors rows in the HF browser cannot be downloaded

`src/tui/hf_dialog.rs:607`, `src/tui/hf_pull.rs:317`

`spawn_hf_search` now passes `WeightFormatFilter::Any` and rows render an `SFTN` badge,
but the file picker still does:

```rust
files.retain(|f| f.filename.to_ascii_lowercase().ends_with(".gguf"));
```

and the downloader sets `extension_filter: Some(".gguf")`. Selecting a safetensors-only
repo (`Qwen/Qwen2.5-0.5B-Instruct`) shows `no ".gguf" files in this repo.` and nothing
can be pulled.

This is load-bearing: vLLM only serves repos already in the HF cache, and the pull flow
is the only in-app route to put one there. The backend currently has no first-party way
to acquire a model. The commit is titled `feat(pull): find safetensors repos in the HF
browser`.

**Fix direction:** the picker and downloader need the same weight-format notion the
search already has. A safetensors repo is a multi-file set (`*.safetensors` +
`config.json` + tokenizer files), not a single-file pick, so the picker's
one-row-per-file model needs a whole-repo row.

#### R1-3 · `--data-parallel` in the denylist matches nothing

`src/backend/vllm/mod.rs:76`

`is_forbidden_head_ext` → `head_hits_prefixes` (`src/launch/params.rs:49`):

```rust
.any(|p| lower == *p || (p.ends_with('-') && lower.starts_with(&p.to_ascii_lowercase())))
```

Only entries ending in `-` prefix-match. `"--data-parallel"` has no trailing dash, so
only a literal `--data-parallel` token is refused — and vLLM spells the family
`--data-parallel-size`, `--data-parallel-rank`, `--data-parallel-address`,
`--data-parallel-backend`.

`llamastash start <repo> -- --data-parallel-size 2` reaches the launcher and spawns
multi-process execution the supervisor cannot own or reap, which is precisely what the
doc comment above the list and `docs/vllm-setup.md:141` promise is refused.

**Fix:** `"--data-parallel-"`. Separately, `"--ray"` is not a vLLM flag at all — Ray is
selected via `--distributed-executor-backend ray`, which is already caught. Drop it or
replace it with something real.

### Correctness

#### R1-4 · `identify` and `served_model_name` diverge outside the HF cache layout

`src/backend/vllm/mod.rs:270` vs `:528`

```rust
// identify
name: discovery::repo_id_for_snapshot(path).unwrap_or_else(|| path.display().to_string()),

// served_model_name
discovery::repo_id_for_snapshot(model_path)
  .or_else(|| model_path.file_name().map(|n| n.to_string_lossy().into_owned()))
  .unwrap_or_else(|| model_path.display().to_string())
```

Same input, two names, whenever `repo_id_for_snapshot` returns `None` — i.e. any
directory outside the HF cache layout. The module's own test pins
`served_model_name("/models/my-model") == "my-model"`.

`vllm_argv` registers `--served-model-name my-model`; the TUI chat path
(`src/tui/events.rs:1644`) reads the identity name and sends
`model: "/models/my-model"`. vLLM validates the model field, so chat 404s **after** a
full cold start.

Note `129e419` changed the chat path specifically to send the backend-minted identity —
which is the right direction, but it makes this divergence the live failure rather than
a latent one.

**Fix:** `identify` should call `served_model_name`. One name, one derivation.

#### R1-5 · CLI and daemon admit directory paths with different predicates

`src/cli/start.rs:319` vs `src/daemon/launch_service.rs:254`

```rust
// cli/start.rs — ungated
if !path.is_file() && crate::backend::synthetic_identity_for_path(&path).is_none() {

// daemon/launch_service.rs — gated
match crate::backend::synthetic_identity_for_path_available(&parsed.model_path, ctx) {
```

The `synthetic_identity_for_path_available` doc explicitly says the ungated form is
wrong for callers that can consult config. With `backend.vllm.enabled: false` (or no
`vllm` on PATH), an HF snapshot directory passes the CLI gate, then the daemon's gated
lookup returns `None` and the path falls into `resolve_model_id_and_arch` →
`read_gguf_header` on a directory. The user sees a raw header/EISDIR error instead of
"no model matches".

**Fix:** both sites use the gated predicate. The CLI has the config; there is no reason
for it to use the weaker form.

#### R1-6 · Non-GGUF admission gate silently skipped when weight bytes are 0

`src/daemon/launch_service.rs:925`

```rust
&& total_weight_bytes > 0);
```

`launch_total_bytes` resolves from the catalog or an on-disk stat. A directory model
launched by absolute path from outside the configured scan roots — now reachable
because of the R1-5 change — yields 0, so the gate never engages. Meanwhile
`resolve_native_knobs` still hands the backend the 8 GiB `DEFAULT_KV_CACHE_BYTES`
default. A 140 GB repo launched that way gets neither a size-aware cap nor a refusal,
and nothing is logged about the gate having been skipped.

**Fix direction:** stat the directory when the catalog has no figure, or refuse the
launch rather than admitting it unguarded. At minimum log the skip — a silent bypass of
a memory guard is the worst of the three options.

#### R1-7 · Directory outside the cache root is undeletable, with a false reason

`src/tui/delete.rs:208` *(reachability is plausible, not confirmed — verify the scan
path first)*

`full_rescan` walks the configured `scan_roots`, so an HF-layout tree under a user
`model_paths` root is enumerated. `hf_repo_dir_in_cache` deliberately returns `None` for
a repo outside `hf_cache_dir()`, so `plan.hf_repo_dir` is `None`. `describe()` then
promises "One file is unlinked", the user confirms, and `execute` hits:

```rust
if plan.primary.is_dir() {
  return Err(io::Error::other(format!(
    "{} is a directory and is not the only model in its cache repo — \
     refusing to delete it", ...
```

The reason is false — it *is* the only model, it is simply outside the cache root — and
there is no other route to remove the row.

**Fix direction:** distinguish "not the only model in its repo" from "outside the
resolved cache root" and say which one applies. The second case can be deleted safely
once confirmed.

#### R1-8 · `served_model_entries` claims truncation tolerance it does not have

`src/daemon/probe.rs:196`

The comment says the find-first-`{` + single-value decode survives "headers in front,
truncated at the read cap, or chunked trailers". Skipping headers and ignoring trailing
bytes works. Truncation does not — `Deserializer::deserialize` on a cut-off object
errors with "EOF while parsing", `served_model_entries` returns `None`, and
`body_serves_expected_id` returns false forever.

`probe_once_body` caps at 16 KiB, `fetch_models_body` at 32 KiB. A server advertising
enough models (a multi-alias `--served-model-name` list, or a multiplexer listing many)
never reaches Ready and never re-adopts, with no diagnostic pointing at the cap.

**Fix:** either implement the stated invariant (accept a partial parse, or scan for the
`data` array specifically) or correct the comment and raise the cap. Leaving a comment
that overstates the guarantee is how this bites someone at 2am.

#### R1-9 · `quant_label` fallback applied at 2 of 5 render sites

`src/proxy/router.rs:576`, `src/proxy/router.rs:661`, `src/proxy/route.rs:409`

Have the fallback:

- `src/discovery/catalog.rs:112`
- `src/tui/list_pane.rs:398`

Do not:

- `src/proxy/router.rs:576` — `quantization_level`
- `src/proxy/router.rs:661` — `general.quantization`
- `src/proxy/route.rs:409`

An AWQ safetensors row reports `AWQ` in `llamastash list` and the TUI, and the `Unknown`
placeholder through the Ollama-compat `/api/tags` / `/api/show` surface.

**Fix:** one accessor on `ModelMetadata`, not a fallback duplicated at each render site.
That also stops the next surface from forgetting it.

#### R1-10 · A stripped flag's dash-leading value survives into argv

`src/backend/vllm/mod.rs:613`

```rust
if skip_value {
  skip_value = false;
  if !lossy.starts_with('-') {
    continue;
  }
}
```

Extras `["--api-key", "-secret"]` strip `--api-key` but push `-secret`, which vLLM reads
as an unknown short option and refuses the whole launch — the same class of failure the
comment above says this logic exists to prevent for `0.0.0.0`. The `-`-leading exemption
also means the guard fundamentally cannot tell a genuine next-flag from a dash-leading
value.

**Fix direction:** decide per-flag whether it takes a value (the denylist knows) instead
of guessing from the next token's first character.

### Efficiency

#### R1-11 · Depth-4 GGUF walk runs for every repo, result usually discarded

`src/discovery/hf_repos.rs:175`

```rust
Classification {
  has_safetensors,
  has_gguf: contains_gguf(snapshot, GGUF_SCAN_DEPTH),
}
```

The only consumer (`enumerate_root:119`) short-circuits on
`class.has_safetensors && !class.has_gguf`. For a GGUF-only cache — the normal shape for
this tool — every repo pays a recursive `read_dir` four levels deep on every debounced
rescan and the answer is never read. This used to be one flat `read_dir` shared with the
safetensors check.

**Fix:** compute `has_gguf` lazily, only once `has_safetensors` is true.

Reading `resolved_cache_bytes` as a free-bytes helper inside a memory-admission path is
actively misleading, which makes this worse than a cosmetic docs nit.

#### R1-14 · `KV_LABEL_W` and `LABEL_W` duplicate one derived value

`src/tui/fmt.rs:192` and `src/tui/tabs/settings.rs:669`

Both are `18`, both carry the same four-line doc comment naming the same two 17-char
labels (`Trust remote code` / `DSpark confidence`). They encode one fact — the longest
label any backend's `NativeKnobDescriptor` registers — with nothing linking them. The
next backend that registers an 18-char label needs both bumped; bumping one reproduces
exactly the `Trust remote codeinherited` misalignment `129e419` just fixed, in whichever
pane was missed.

**Fix:** one shared constant, ideally computed from `native_knobs()`.
