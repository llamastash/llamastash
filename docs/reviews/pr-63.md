## How to verify a finding before you fix it

Each entry gives a file:line and the call path. Read the path, don't trust the summary.
Project constraints that shape acceptable fixes:

- `CLAUDE.md` § backend no-leak contract: no backend id-string or name, in code **or
  comments**, outside `src/backend/<id>/`, `src/backend/mod.rs`, and the typed config
  struct. Several fixes below are tempting to write as `== "vllm"` — don't; use a trait
  method.
- `CLAUDE.md` § docs ship with code: a behavior fix updates the affected doc in the

- Tests: `make test` (it carries `--features test-fixtures`; forgetting it is the
  classic failure). E2E for anything user-visible — a green suite is explicitly not
  sufficient here, and round 1 found defects the suite passed straight through.

## Round 1 — full-branch review (14 findings, all open at `ebabd23`)

### Blocking

#### R1-1 · `gpu_memory_utilization` disables both memory guards

`src/backend/vllm/mod.rs:413`

```rust
if user_set(params, "kv_cache_memory_bytes") || user_set(params, "gpu_memory_utilization") {
  return out;
}
```

`resolve_native_knobs` returns early, so `kv_cache_memory_bytes` is never inserted. The
non-GGUF admission gate in `src/daemon/launch_service.rs:919-951` derives demand solely
from `admission::resolved_cache_bytes(&launch_params)`, which matches a knob id ending
in `cache_memory_bytes`. Absent here → `None` → `demand` is `None` → `try_admit` never
runs.

Net: `start <safetensors repo>` with `gpu_memory_utilization=0.9` on a 121 GB unified
host gets neither the byte cap nor a pre-spawn refusal. The commit pair "make the KV cap
fail safe" + "apply the admission gate to non-GGUF launches" both no-op on exactly the
configuration that has frozen this hardware before.

**Fix direction:** the two knobs are not interchangeable. `kv_cache_memory_bytes` set by
the user is a real opt-out; `gpu_memory_utilization` set by the user still needs the
admission gate to see a demand figure. Either derive a byte figure from the utilization
fraction and feed it to `resolved_cache_bytes`, or keep the gate engaged with the
pool-fraction demand computed separately.

#### R1-2 · Safetensors rows in the HF browser cannot be downloaded

`src/tui/hf_dialog.rs:607`, `src/tui/hf_pull.rs:317`

`spawn_hf_search` now passes `WeightFormatFilter::Any` and rows render an `SFTN` badge,
but the file picker still does:

```rust
files.retain(|f| f.filename.to_ascii_lowercase().ends_with(".gguf"));
```

and the downloader sets `extension_filter: Some(".gguf")`. Selecting a safetensors-only
repo (`Qwen/Qwen2.5-0.5B-Instruct`) shows `no ".gguf" files in this repo.` and nothing
can be pulled.

This is load-bearing: vLLM only serves repos already in the HF cache, and the pull flow
is the only in-app route to put one there. The backend currently has no first-party way
to acquire a model. The commit is titled `feat(pull): find safetensors repos in the HF
browser`.

**Fix direction:** the picker and downloader need the same weight-format notion the
search already has. A safetensors repo is a multi-file set (`*.safetensors` +
`config.json` + tokenizer files), not a single-file pick, so the picker's
one-row-per-file model needs a whole-repo row.

#### R1-3 · `--data-parallel` in the denylist matches nothing

`src/backend/vllm/mod.rs:76`

`is_forbidden_head_ext` → `head_hits_prefixes` (`src/launch/params.rs:49`):

```rust
.any(|p| lower == *p || (p.ends_with('-') && lower.starts_with(&p.to_ascii_lowercase())))
```

Only entries ending in `-` prefix-match. `"--data-parallel"` has no trailing dash, so
only a literal `--data-parallel` token is refused — and vLLM spells the family
`--data-parallel-size`, `--data-parallel-rank`, `--data-parallel-address`,
`--data-parallel-backend`.

`llamastash start <repo> -- --data-parallel-size 2` reaches the launcher and spawns
multi-process execution the supervisor cannot own or reap, which is precisely what the
doc comment above the list and `docs/vllm-setup.md:141` promise is refused.

**Fix:** `"--data-parallel-"`. Separately, `"--ray"` is not a vLLM flag at all — Ray is
selected via `--distributed-executor-backend ray`, which is already caught. Drop it or
replace it with something real.

#### R1-6 · Non-GGUF admission gate silently skipped when weight bytes are 0

`src/daemon/launch_service.rs:925` — **the existing mitigation is unreachable**

The code already contains the right fallback, and a guard one level up stops it running.

#### R1-8 · `served_model_entries` claims truncation tolerance it does not have

`src/daemon/probe.rs:196`

The comment says the find-first-`{` + single-value decode survives "headers in front,
truncated at the read cap, or chunked trailers". Skipping headers and ignoring trailing
bytes works. Truncation does not — `Deserializer::deserialize` on a cut-off object

**Fix:** either implement the stated invariant (accept a partial parse, or scan for the
`data` array specifically) or correct the comment and raise the cap. Leaving a comment
that overstates the guarantee is how this bites someone at 2am.

#### R2-2 · The 512 MiB KV floor makes the admission gate unable to refuse

`src/backend/vllm/mod.rs:540-545`, doc claim at `:491-496`, gate at `src/daemon/launch_service.rs:961-994`

```rust
fn kv_cache_cap_bytes(free_bytes: u64, weights_bytes: u64) -> u64 {
  free_bytes
    .saturating_sub(weights_bytes)
    .saturating_sub(UNIFIED_HOST_RESERVE_BYTES)   // 8 GiB
    .clamp(MIN_KV_CACHE_BYTES, DEFAULT_KV_CACHE_BYTES)   // 512 MiB … 8 GiB
}
```

Worked example — unified AMD host, sampled, `ram_free` 60 GiB, 54 GiB repo, `--ctx 32768`:

1. Sampled + unified branch (`:435-438`); `effective_free_bytes` returns
   `min(ram_free, gtt_free)` at `usable_fraction(IntegratedUma) = 1.0` → **60 GiB**.
2. `kv_cache_cap_bytes(60, 54)`: `60-54 = 6`, `6-8 →` saturating **0**, clamped up to
   **512 MiB**.
3. That is written to `backend_knobs` and logged with the same `"vllm: capping KV cache
   at N bytes"` line a healthy host prints. `native_resolution.warnings` stays empty, so
   `start` and the TUI say nothing.
4. Gate: demand = `resolved_cache_bytes` (512 MiB) + weights (54 GiB) +
   `overhead_band_bytes` (512 MiB) = **55 GiB**.
5. `try_admit(port, 55 GiB, 60 GiB)` → 55 ≤ 60 → **admitted**, leaving <5 GiB where
   `UNIFIED_HOST_RESERVE_BYTES` says leave 8.

Generalizing: the floor engages when `weights > free - 8.5 GiB`; the gate refuses when
`weights > free - 1 GiB`. That leaves a ~7.5 GiB-wide band of `weights` where the OS
reserve is silently abandoned **and the gate provably cannot fire** — because the floor
shrank the very term the gate evaluates. The comment at `:494-496` ("the admission gate
is what refuses such a launch, and it can only do that because the figure exists")
asserts the opposite of what the arithmetic does.

Second-order: 512 MiB of KV is roughly 1.6k tokens for an 80-layer GQA model, so the
admitted launch pays a full multi-minute cold weight load before the engine discovers it
cannot honour `--max-model-len 32768` — precisely the pre-spawn refusal the gate exists
to provide.

Note the floor is deliberate and unit-tested (`:951-953` pin
`kv_cache_cap_bytes(10 GB, 8 GB) == MIN_KV_CACHE_BYTES`), so this is a design conflict,
not a slip. The fix has to decide which invariant wins.

**Fix direction:** the gate must evaluate demand against the *requested* context, not
against a floor the resolver already clamped. Either pass the pre-clamp figure to
admission, or have the resolver refuse outright when the clamp engages rather than
emitting a floor and delegating a refusal that cannot happen.

### `scripts/vllm/uat.sh` (new in `ebabd23`, never previously reviewed)

#### R2-3 · Every stage reads `.models[0]`, which is always the *first* launch

`scripts/vllm/uat.sh:16-19`, used at `:54, 64-65, 72-73, 77-84`

`state()`, `pid_of()`, `argv_of()` and `cap_of()` all read `.models[0]`. No stage stops
the previous launch. Following the README's own sequence
(`clean`→`boot`→`launch`→`replay`→`preset`→`chat`→`stop`):

1. `launch` starts the model as `L1` with `--ctx 3072`.
2. `replay` runs `$LS start "$MODEL"` again. `start_model_handler`
   (`src/ipc/methods.rs:524-534`) has no duplicate-launch check — it mints a fresh
   `LaunchId` (`src/daemon/registry.rs:67-70` → `"L2"`) and a fresh port, or fails.
3. Either way `.models[0]` stays `L1`: the registry is a
   `BTreeMap<LaunchId, ManagedModel>` keyed by the `String` `"L1"`/`"L2"`
   (`src/daemon/registry.rs:40`), `snapshot()` (`:85-93`) iterates in key order, and
   `status_response` / `status_json` preserve it (`src/ipc/status.rs:32,145`,
   `src/cli/output.rs:655-694`).
4. `replay` then prints `cap-in-argv:` and `max-model-len: --max-model-len 3072` read
   from **L1's** `/proc/<pid>/cmdline` and reports it as proof that `last_params`
   replayed.
5. `preset` prints the same L1 argv and reports the preset's `kv_cache_memory_bytes`
   "won" even if `--preset vllm-small` was rejected or never applied.
6. `chat` curls `.models[0].port` — L1's port.

Three of five stages report a green result derived entirely from stage one, and the two
behaviours the script exists to prove (`last_params` replay, preset precedence) are
never observed.

**Fix:** capture the `LaunchId` that `start` returns and select on it
(`.models[] | select(.id == $id)`), and stop the prior launch between stages.

#### R2-4 · No `-e`, hardcoded `cd`, and no assertions — every stage exits 0 unconditionally

`scripts/vllm/uat.sh:4-5, 39-44, 50-87`

Two reproducible paths to a false pass:

**(a) Wrong checkout.** Line 5 is `cd /mnt/work/Workspace/oss-libs/llamastash-rs/llamastash`
— an absolute path to one machine's tree. In a clone anywhere else the `cd` fails;
line 4 is `set -uo pipefail` with **no `-e`**, so execution continues in the caller's cwd
and `LS=./target/debug/llamastash` resolves relative to wherever the user happened to be.
Every `$LS` call fails, `cap_of` prints `MISSING`, `wait_settled` spins 90×2 s and prints
`timeout`, and the `case` returns the status of its last command — an `echo` — so the
script exits **0**. The CLAUDE.md rule the script is honouring (never invoke a bare
`llamastash`) is violated in the opposite direction: it runs *nothing*.

**(b) Backend absent** — verified on this machine: `command -v vllm` finds nothing (the
venv is at `~/.venvs/vllm`, not on PATH), so `VllmBackend::available`
(`src/backend/vllm/mod.rs:280-288`) is false. `boot` still prints `catalog=N>0` because

then hits `src/daemon/launch_service.rs:270-281` and errors with "is served by the
`vllm` backend, which is not available"; `tail -1` swallows it into one line, `cap_of`
prints `MISSING`, and the stage exits **0**.

`scripts/vllm/README.md` states `launch # explicit --ctx; asserts the KV cap reached
argv`. There is no assertion in the file — every branch terminates in `echo`. Any
wrapper doing `uat.sh launch && echo PASS`, or a `make` target, records a pass for a run
in which nothing launched.

**Fix:** `set -euo pipefail`; derive the repo root from `${BASH_SOURCE[0]}`; make each
stage `exit 1` on a failed expectation; gate the whole run on the backend actually being
available.

  DPCoordinator and spawned APIServer processes — so `VLLM::` matches every vLLM engine
  process the user can signal.

So running `uat.sh clean` while the user's normal daemon has a vLLM model resident kills
that model's children. The real daemon's supervisor then records a crash for a model
nobody asked to stop, and line 35 prints `clean: RAM=…M vllm_procs=0` — success — for
having reaped someone else's work.

**Fix:** scope the kill to the isolated daemon's own children (walk the pids the isolated
`status --json` reports, or match on the UAT state dir in the command line).

### Maintainability

#### R2-6 · The 18-wide label column has one column of slack and no test

`src/tui/fmt.rs:192`, `src/tui/tabs/settings.rs:669` — *extends R1-14*

The width is a cross-module contract: the data lives in backend modules
(`src/backend/vllm/mod.rs:147` `"Trust remote code"`, `src/backend/ds4/mod.rs:387`
`"DSpark confidence"`, both 17) and the renderer is generic (`format!("  {label:<width$}")`
at `src/tui/fmt.rs:219,254` and `src/tui/tabs/settings.rs:691`). Nothing enforces it —
grepping `KV_LABEL_W`/`LABEL_W` across the tree returns only the two definitions and the
three `format!` sites. No test.

The four goldens updated in this commit (`dashboard-overview`, `hf-confirm`, `hf-files`,
`hf-search`) contain only llama.cpp typed-knob labels (`ctx`, `reasoning`,
`n_gpu_layers`, `n_cpu_moe`, `flash_attn`, `cache_type_k`, `cache_type_v`, `threads`,
`launch` — max 12 chars), and `tests/tui_e2e_render_test.rs` renders no ds4/vLLM knob
panel. **No snapshot exercises a 17-char label, before or after this fix.**

Concrete regression: add a vLLM knob labelled `"KV cache dtype size"` (19) — or any
18-char label — and `{label:<18}` emits it with zero trailing pad, `kv_row` concatenates
the value span directly onto it (`src/tui/fmt.rs:217-223`), giving
`KV cache dtype sizeinherited`. All 7 golden tests still pass, `make lint` passes, and
the only signal is a human looking at the pane.

The contract also cuts the other way: both comments now name backend-owned label strings
from generic TUI files, which brushes against the no-leak rule — deleting a backend
module leaves the justification for the constant dangling.

**Fix:** one constant derived from `native_knobs()` at build or test time, plus a test
that renders the longest registered label and asserts a gap.
